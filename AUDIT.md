# Аудит кода: `legacy/utils.py` и `legacy/api.py`

Аудит проведён вручную и подтверждён статическим анализом (`ruff check legacy --select E,W,F,B,S,N,SIM` — 30 замечаний) и запуском уязвимых сценариев через Flask test client. Исправленная версия находится в `app/`; папка `legacy/` оставлена без изменений как «до».

**Шкала критичности:**

- **Критическая** — эксплуатируемая уязвимость или утечка данных.
- **Высокая** — падение сервиса, порча данных, неверная логика авторизации.
- **Средняя** — утечки ресурсов, некорректные ответы API, гонки без немедленного ущерба.
- **Низкая** — стиль, читаемость, сопровождаемость.

## SQL-инъекции подробно

В коде четыре точки, где пользовательский ввод склеивается с SQL-текстом: `utils.py:11` (f-строка), `utils.py:32` (`%`), `api.py:15` и `api.py:21` (конкатенация `+`). Во всех случаях СУБД получает ввод как часть кода запроса, а не как данные.

### 1. Чтение чужих данных через `/user/<uid>` (api.py:21)

```python
q = "SELECT id, name, tags FROM users WHERE id = " + uid
```

`uid` подставляется без кавычек, поэтому атакующему даже не нужно закрывать строку.

| Атакующий ввод (`uid`) | Итоговый SQL | Результат |
|---|---|---|
| `0 OR 1=1` | `... WHERE id = 0 OR 1=1` | условие всегда истинно, возвращается первый пользователь |
| `0 UNION SELECT 1, sqlite_version(), sql FROM sqlite_master` | `... WHERE id = 0 UNION SELECT ...` | утечка версии СУБД и схемы всех таблиц |

Реальный вывод на legacy-коде:

```
/user/0 OR 1=1     -> 201 {'id': 1, 'name': 'alice', 'tags': '[]'}
UNION-инъекция     -> 201 {'id': 1, 'name': '3.50.4',
                           'tags': 'CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, tags TEXT)'}
```

Тем же способом через `UNION SELECT` читаются любые таблицы, например будущие хеши паролей.

### 2. Подмена данных через `/adduser` (api.py:15)

```python
conn.execute("INSERT INTO users (name, tags) VALUES ('" + n + "', '[]')")
```

Атакующий JSON:

```json
{"name": "x', '[]'), ('hacked', '[\"admin\"]') --"}
```

Итоговый SQL — вместо одной записи вставляются две, а хвост запроса закомментирован:

```sql
INSERT INTO users (name, tags) VALUES ('x', '[]'), ('hacked', '["admin"]') --', '[]')
```

Реальное содержимое таблицы после запроса:

```
[('alice', '[]'), ('bob', '[]'), ('x', '[]'), ('hacked', '["admin"]')]
```

Атакующий сам выбирает значения полей — в том числе теги или роли, от которых зависит авторизация.

### 3. `utils.add_user` и `utils.get_user_by_name` (utils.py:11, 32)

Тот же класс уязвимости: `get_user_by_name("' OR '1'='1")` превращается в `WHERE name = '' OR '1'='1'` и возвращает первого пользователя без знания имени. Это обход проверки при поиске по логину.

Почему не сработает `DROP TABLE`: классический пейлоад `x'); DROP TABLE users;--` здесь падает с `OperationalError: 1 values for 2 columns`. Подогнанный под две колонки `x', '[]'); DROP TABLE users;--` всё равно отклоняется: `sqlite3.Cursor.execute` выполняет только одно выражение (`ProgrammingError: You can only execute one statement at a time`). Это случайная защита драйвера, а не исправление: `UNION`, многострочный `VALUES` и подзапросы работают. С другим драйвером или через `executescript` таблица была бы удалена.

### Исправление

Только параметризованные запросы — драйвер передаёт значения отдельно от текста SQL, и они никогда не интерпретируются как код:

```python
conn.execute("INSERT INTO users (name, tags) VALUES (?, ?)", (name, json.dumps(tags)))
conn.execute("SELECT id, name, tags FROM users WHERE id = ?", (user_id,))
```

Дополнительно `uid` ограничен конвертером `<int:uid>`, поэтому `/user/0 OR 1=1` вернёт 404 ещё на уровне маршрутизации. В `tests/test_api.py` есть тест: имя `x'); DROP TABLE users;--` сохраняется как обычная строка, а таблица остаётся целой.
